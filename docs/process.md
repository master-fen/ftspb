# Процесс

Как ведётся работа над проектом: кто что решает, в каком режиме работает
агент, чем доказывается правка, какой ритуал у опасных операций. Условия
мержа, префикс `[миграция]` и запреты на переписывание истории — в
`CLAUDE.md`, здесь они не дублируются.

## Роли

- **Антон** — аналитик и руководитель, вайб-кодер: запускает команды по
  инструкциям, решения принимает сам.
- **Claude** (чат) — постановщик задач и рецензент. Требует проверки фактом:
  буквальный вывод, не пересказ; «готово» без выводов не принимается. Диффы и
  мержи читает по собственному клону. Числа из докладов пересчитывает сам, где
  это возможно. Собственные утверждения по памяти помечает и просит
  первоисточник.
- **Claude Code** — исполнитель. Ветки `claude/*`, PR через `gh`.

## Режимы и цикл задания

- **Plan mode** — для заданий с развилками: агент исследует и предлагает план,
  план идёт на ревью, правки — списком, одним текстом.
- **Auto** — для исполнения готового отрецензированного плана и для мелких
  заданий.
- `/clear` перед каждым заданием: контекст прошлого задания мешает и
  подменяет факты устаревшими.
- Цикл: постановщик готовит промпт → Claude Code в plan mode (или auto) →
  план на ревью → исполнение → доклад → ревью диффа по клону. Ревью содержимого
  задания — до промпта, по первоисточникам.
- **Ревью плана ловит то, чего не ловит исполнение**: тесты, проходящие при
  подмене плашек местами; хрупкий шаг пробы; отсутствие замера порога; двойное
  закрытие и автоповтор клавиш. Самую хитрую часть агент может исследовать и
  планировать без присмотра, а исполнять — при человеке.
- **Длинный промпт передаётся файлом** (`ИМЯ.local.md`, под `.gitignore` по
  шаблону `*.local.*`) и строкой «прочитай и выполни»: вставленный в чат текст
  обрезается, и агент достраивает недостающее сам. При человеке у машины
  обрезанное задание на операцию записи — повод спросить, а не угадывать.
- **Доклад — файлом** в `batch.local\`; в чат — итог. Рассказ агента о ходе
  работы отчётом не является.

## Сессии с телефона

Сессии Claude Code с телефона создают ветки вида `claude/НАЗВАНИЕ-xxxxxx` с
автором `Claude`. Такая ветка не мержится без чтения диффа по клону и без
локального ритуала (`git status`, `git pull --ff-only`, проверка двух
родителей у merge-коммита).

## Уровень проверки — по риску, выбирается до промпта

- Данные, миграции, секреты, безопасность — полный ритуал.
- Общие токены и примитивы `ui/*` — средний: зелёный CI, снимки, пробы на 390
  и на широком экране, мутационные контроли.
- Визуальная правка на нескольких страницах — лёгкий: зелёный CI, пробы,
  взгляд. Дешёвое доказательство снимками входит в лёгкий уровень, когда
  разметка меняется известным образом.

Перед добавлением проверки — вопрос: что сломается на сайте, если этого не
проверять.

## Снимки как доказательство — три формы

- **(а) Правка вне SSR** (портал, обработчики, эффекты): ожидание «все страницы
  совпали» по построению, и обязателен положительный контроль — копия стороны
  B с дописанным байтом обязана дать на одну страницу меньше и код выхода 1.
  Иначе «совпало» неотличимо от сравнения каталога с самим собой.
- **(б) Разметка меняется на известном множестве страниц**: таблица ожиданий
  по снимку «до», остальные страницы — байт-в-байт.
- **(в) Для изменённых страниц**: вырезать изменяемый блок с обеих сторон,
  остаток сравнить побайтно, с печатью чисел по каждой стороне.

Порядок строки манифеста между двумя сборками недетерминирован — инструмент
сортирует, это не находка.

## Стоп-условия

- **Стоп-условие, сработавшее по букве, исполнитель не толкует** — даже если
  смысл выполнен: показать вывод и ждать. Толкование бывает верным, но откат
  после мержа — это обратный merge-коммит и автодеплой. Строка входит в каждый
  промпт.
- **Стоп-условие про CSS формулируется пробой, grep — диагностика.** Условие
  «в собранном CSS есть `@media (max-height: 479px)`» не учло range-синтаксис
  сборки; следствие (`display: none` при высоте окна 420) проверяла проба.
- **Проверка, добавленная на ревью, называет свой статус** — стоп-условие или
  замер.
- **Проба до правки красная по правильной причине.** Если на `main` сценарий
  невозможен вовсе, «красное» ничего не доказывает: правка выделяется отдельным
  коммитом и проба гоняется на промежуточной сборке.
- **Неизменное число тестов — тоже сторож.** В PR без тестов (портал не виден
  `renderToStaticMarkup`, DOM-окружения для тестов нет) число обязано остаться
  прежним; тест ради схемы коммитов не изобретается. Дробность — по тесту на
  строку таблицы, имя теста называет строку.

## Операция над данными в S3 — полный ритуал

- Бэкап вне временных каталогов, со сверкой с текущим состоянием объекта
  (md5 файла равен ETag объекта) непосредственно перед записью.
- Результаты кодируются один раз и сверяются с тем, что человек смотрел
  глазами.
- Пилот с настоящим откатом.
- Запись тем же путём, что пишет приложение (`uploadObject` из
  `src/server/storage.ts`).
- Проверка каждой записи со стороны анонимного читателя (HEAD и GET).
- Первая неудача — откат ключа и остановка.
- Итог — точная сумма из манифеста и идемпотентный повторный план («уже
  сделано N, к записи 0»).

**Сложность — в скрипте, не в человеке:** одна остановка там, где нужны глаза;
отдельные «да» на автоматические фазы — лишнее. Перестраховка — тоже дефект.

## Ритуал миграции БД на проде

1. Логический бэкап базы (вручную в панели хостинга).
2. Ветка PR выкачивается локально.
3. Новое окно cmd; переменные окружения задаются `set` отдельными строками.
4. `bun run db:migrate` для схемы `dev`, затем для `public`.
5. Факт применения проверяется запросом к `information_schema.columns` или
   `pg_indexes` — не по выводу мигратора.
6. Окно закрывается.
7. Только после этого — мерж.

PR с миграцией мержит Антон, не агент; правило и определение такого PR — в
`CLAUDE.md`, «Правила PR».

## Схема коммитов

- Тест-сторож — отдельным коммитом, его краснота доказана выводом; затем
  правка; затем документы.
- Коммиты несут трейлер `Co-Authored-By`.
- Изменение инструмента сверки — отдельный коммит, тест, отрицательный
  контроль.
- Одноразовые скрипты живут в scratchpad, инструментами не являются и не
  коммитятся.
- `src/routeTree.gen.ts` руками не правится.
- Lint сравнивается списком предупреждений, не их числом.
- `taskkill /IM` не применять — только по конкретному PID.

## Автономный пакет (Антона нет у машины)

- Ничего не мержится и не создаётся PR — ветка только пушится.
- Ничего не пишется в S3 и в БД.
- `package.json` не трогается.
- Браузер не используется.
- Правила — файлом (`ИМЯ.local.md`), перечитывать перед каждым заданием: после
  сжатия контекста правила из переписки теряются.
- Запреты дублируются в стартовом сообщении: классификатор auto-режима видит
  сообщения, но не содержимое файлов.
- Дымовая фаза собирает все разовые запросы в первые минуты.
- Отчёты — файлами в `batch.local\`, с разделом «Решено без Антона».
- Задания независимы: стоп одного не держит следующее.
- Запрет, заданный словами, снимается только явно.

## Факты о Claude Code

Со слов Среза 29, 19.09.2026 (сверено там по документации `code.claude.com`
18.09.2026); по репозиторию не сверяется:

- В auto-режиме действия проверяет классификатор; после трёх блокировок подряд
  или двадцати за сессию режим встаёт на паузу и спрашивает.
- Запреты из переписки теряются при сжатии контекста. Жёсткая гарантия —
  deny-правило в `.claude/settings.local.json` (файл под шаблоном `*.local.*`
  в `.gitignore`, в репозиторий не уходит).
- Через Remote Control запросы приходят в приложение; выбрать режим Auto из
  приложения нельзя.

## Четыре класса утверждений — у каждого свой проверяющий

- О коде и репозитории — агент по клону, буквальным выводом команды.
- О данных, S3 и проде — команды на чтение.
- Решения и намерения Антона — только он.
- Внешний мир (секретарь федерации, дизайнер) — только он.

Утверждение о коде, перенесённое из документа без сверки, — гипотеза, а не
факт: документ врёт там, где его не трогали.
